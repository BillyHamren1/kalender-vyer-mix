1. Parent re-verifies the exact hosted project/baseline and executes only the approved metadata query with bounded response handling. Retain the complete redacted result and exact query/result hashes. Classify `unavailable`, each false/null predicate, and descriptive facts separately; do not create a mismatch from an absent candidate that is expected at baseline.
2. If a structural predicate is false, prepare a separately reviewed additive proposal from actual catalog identities. A uniqueness proposal requires an explicitly authorized duplicate/null/tenant-identity audit before any DDL; never delete, merge or reassign profiles/roles to make it pass. A named-index difference can require preserving the existing index plus a reviewed equivalent exact-name index, or an explicitly versioned migration contract amendment. Neither action is authorized here, and a redundant index needs its own locking/performance review.
3. An FK discrepancy requires an actual referential and managed-auth deletion-policy audit. Adding a CASCADE FK beside an existing restrictive FK does not prove the combined deletion behavior is correct. Do not drop/retarget a provider FK, delete orphan role rows, silently validate dirty history, or infer a replacement auth identity. Any future validation/constraint addition needs an approved source-specific, data-preserving migration and realistic managed-provider staging tests.
4. A declared-owner capability discrepancy requires identifying the real installer and final definer owners first. Review exact schema/function privileges and all containing owner chains; do not assume hosted `postgres` is a superuser or that native fixture ownership is the provider owner. Any future narrow grant needs an explicit privilege/rollback plan and provider/JWT proof. Broad PUBLIC/anon grants, auth.uid replacement and role promotion are outside this proposal.
5. Rehearse the exact candidate dependency graph on an isolated production-faithful schema with separately captured auth/role/catalog facts. Re-run complete installed guards, effective ACL/owner callers, queued writers, signed API, no-write state and existing application regressions. Synthetic bootstraps are test models only. ## Failure and rollback policy

No deployment or rollback runs here. A preflight refusal keeps the candidate blocked; do not catch its error and continue later DDL. An atomic installation failure must roll back all wrapper/ACL/function changes and leave source data and earlier immutable evidence untouched. If the real runner can commit a partial `130228`, that runner is an unresolved blocker until an atomic path is reviewed and tested.

For a post-install regression, default-off reader/product gates and feature visibility are the first containment controls. A rollback proposal must use an exact before/after function/ACL manifest and actual dependent owner callers. Blindly restoring old direct private EXECUTE or old public routing can reintroduce the queued-writer bypass/availability risk; it is not an automatically safe rollback. Do not drop a shared namespace, whole evidence table, baseline/history or newly used compatible function. A future function/ACL rollback needs independent dependency review, atomic staging fault injection and application compatibility evidence. Any separately proposed prerequisite index/FK/grant also needs an explicitly owned reversal strategy that preserves established identities and managed auth behavior.

There is no hosted installation approval, production data remediation, source-authority admission or complete catalogue certificate in this document.
