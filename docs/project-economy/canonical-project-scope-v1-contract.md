## Scope identity and ownership

A new `economic_scope_id` identifies an Operations-owned economic aggregate. It is a new ledger identity, **not** a fabricated `public.projects` row. Its organization, root kind (`project`, `large_project`, `packing_project`) and existing root UUID are immutable. Root kinds remain distinct even when UUID spellings coincide.

Enrollment captures a complete, versioned set of existing personnel allocation project IDs and Booking IDs. All members are explicit. The database verifies same organization, root validity and relationship evidence; a caller cannot supply captured relationship rows, hashes, actor or organization. Existing `source_project_id` values remain unchanged in the current personnel v1 protocol. Economic-scope projection is a separate join, not a source correction.

Operations-local `bookings.id` and relationship booking columns are **text**, as proved by the actual migrations. Legacy text IDs are retained exactly. They are not automatically canonical Booking UUIDs. A future trusted Booking mapper needs a separately versioned explicit `(Operations organization, local booking ID) → (Booking source organization, canonical Booking UUID)` enrollment. UUID resemblance or matching display numbers is not authority. No local ID is lowercased or cast to UUID. Several legitimate allocation projects may refer to one local booking; the complete scope records those relationships and deduplicates the underlying economic sources instead of rejecting this operational view overlap.

Ownership reservations are exclusive per organization and source project/booking. An already-owned member cannot be silently moved to another scope. Initial enrollment has no transfer/delete API. Removal from a later complete membership snapshot **retains the original permanent reservation**; this bounded v1 API cannot release or transfer it. A future transfer requires explicit old/new scope revisions, historical lineage, source-cost reconciliation and a Finance mapping revision. Packing references and other operational views may overlap, but they do not independently own/charge the same source under this contract.

Snapshots are immutable complete replacements under an expected revision and idempotency key. Authenticated organization admin authorization is derived from `auth.uid()`, a unique current `profiles.user_id` row and actual same-org `user_roles.role='admin'`. No caller actor/organization parameter exists. The transaction captures current roots and source rows, locks membership ownership, validates complete relationships, appends the snapshot and advances the saved head atomically. Changed same-key requests conflict; stale commands never change a head. Update/delete/truncate of immutable snapshots are denied.

The initial command is exact eight fields: `schema='operations-project-scope-enroll.v1'`, `economic_scope_id`, `root_kind`, `root_id`, `expected_revision`, `expected_membership_fingerprint`, `idempotency_key`, `reason`. An admin-only preview reads the whole actual same-org relationship set and displays explicit root/project/local-booking IDs and its fingerprint. Enrollment repeats those reads in the transaction and requires that exact preview fingerprint; the admin does not supply relationship rows or economic amounts. Roots with no bookings can capture a genuine internal project with the root project itself. Any additional ambiguous or changed membership invalidates the preview; legacy-only mirrors do not become members.

Implemented RPCs are `preview_operations_project_scope_v1(p_root_kind text,p_root_id uuid)` and `enroll_operations_project_scope_v1(p_command jsonb)`. Public functions are invokers; private empty-search-path definers derive the real actor/org and have narrowly granted authenticated execution. Direct client table access and anonymous/service impersonation are denied. Existing auth/profile/admin-role rows are locked against revocation during the transaction. Packing needs a matching enabled row in service-managed `operations_project_scope_packing_policies`; its default is disabled, and the matching policy row is locked against revocation. This policy does not activate costs or transport.

One CTE/SQL statement captures the entire relevant root/join/project-leaf/local-booking catalog coherently. All subsequent membership derivation uses that captured JSON, rather than mixing successive READ COMMITTED source snapshots. Existing root rows are locked. This is an **as-of relationship snapshot**; new source edges can exist after it, and no perpetual graph currentness or economic coverage is claimed. A fresh preview re-reads the graph. Future cost activation must verify the enrolled revision is still current.

Project/packing snapshots retain the actual UUID of each live parent master join. Replacing a parent edge changes the fingerprint even when its booking endpoint is unchanged. Duplicate same-parent master joins are rejected consistently for every root kind; multiple distinct project leaves sharing a booking remain valid. UTF8 byte ordering matches PostgreSQL C collation; source UUIDs normalize case and legacy text IDs retain exact characters. Text bounds use Unicode scalar character counts and trim whitespace; output caps are 1000 bookings and 1000 project leaves. The command's expected revision is at most `9007199254740990`, so the next saved revision stays a safe integer.
