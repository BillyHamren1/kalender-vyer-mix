## First supported transition

The first extension is **current-source snapshot export only** for a single permanent Operations organization/economic scope → Finance organization/whole destination. It must not support withdrawal, retirement, alternate owner, aliases, component-based full-scope inference, or historical source proof. Those require later explicit protocols. Disablement blocks disclosure/new sending; it does not manufacture a zero snapshot, delete an obligation or withdraw an already saved Finance amount.

The product remains partial invoice/obligation evidence. It copies the unchanged server calculation and preserves unavailable source/category coverage, NULL EAC/budget/margin/remaining, unresolved credits and saved receiver-head/as-of graph labels. Time, Catering, historical rates and hired-personnel classifications are not made complete by export. Finance must neither add components to this whole copy nor calculate a replacement total.

## Operations-authenticated export grant

A NEW authenticated command supplies identity, optimistic versions, idempotency and audit reason only. A command's proposed selectors are organization/economic scope; expected scope snapshot/revision/membership fingerprint; expected composition snapshot/revision/fingerprint; expected grant revision; explicit destination Finance organization/whole scope; declared Finance mapping event/revision/fingerprint; idempotency key/reason. Exact command field count/schema and grant-event canonical tuple require a separate helper/SQL lock before implementation. No caller actor, source capture, price, projection, proof-success flag, Finance recipient or enablement surrogate is accepted.

Actual actor comes from the live authenticated user/profile/organization-admin relationship. The writer must check the complete canonical permission project union, including projects of all captured obligations, with immutable hinted discovery and same-or-stronger SHARE NOWAIT protection on auth/profile/admin/project/root/current packing-policy/gate rows. Changed discovered identities/permission sets cause PT409 before new late row locks are acquired. Use existing verified authorizers and compatible capture entry; do not invent a grant from an alias preview or reuse a service identity as an operator.

A grant event is immutable and captures actual current full canonical membership, scope/composition identities and fingerprints, actual actor/time/reason, declared destination/mapping tokens, previous expected revision and canonical command fingerprint. A current head may advance only to a saved matching event; it cannot change stream identity or rewind. An exact idempotent historical receipt must remain historical and cannot re-enable the event. Service permissions are SELECT-only for audit/heads/events; configuration retains only specifically reviewed enabled-column updates. Owner-level immutable/no DELETE/TRUNCATE and matching-head guards are still required.

First successful grant permanently reserves `(source organization, economic scope)` to `(Finance organization, destination whole scope)`. Every later event retains that owner, including disabled events. Reservations protect absent first rows; no ownership decision depends only on existing head row locks. Competing first destinations must serialize or fail without either partial event or owner reassignment. The exact reservation keys/order must align existing scope reservation and publication/permission order before SQL approval.

Declared Finance mapping tokens identify the operator's intended target; they are **not remotely verified Finance rights**. Operations cannot inspect live Finance membership/project rights within its database. A signed export proof must expose only the locked grant7 projection of the actual event: event_id, revision, fingerprint, destination_organization_id, destination_scope_id, destination_mapping_id, destination_mapping_revision. ## Finance verification and atomic local admission

Finance first uses its actual current metadata foundation: active recipient auth user and membership, admin/finance_admin or every member's project_access; live same-org projects/currency; current enabled entity/map/share heads; exact full source membership and captured component-pair bijection; permanent source/destination ownership; delivery gate and exact purpose enrollment. Actor `can_access_project` cannot establish a different recipient's rights. Source manifest rows cannot reconstruct complete membership. Metadata stays declared_unverified/transportfalse until genuine source and admission protocols are implemented.

A NEW protected receiver may fetch a source proof outside its final Finance database transaction with bounded native HTTPS. That fetch acquires no reusable Finance row lock and grants no local authority. The final SQL transaction must independently verify the **actual signed raw request/response packet** against a server-maintained enrolled source-verification secret/key, exact purposes, request body hash, nonce, expiry, destination body SHA, response scopes/current head and grant7. No verified boolean, arbitrary service-issued token, caller actor, detached signature sidecar or TS-only precheck authorizes cost. Database secret lookup/crypto, key revocation and wrapper EXECUTE boundaries require an explicit reviewed implementation; passing the pure helper output alone is insufficient.

In that same transaction, recheck actual live Finance foundation/full rights and body mapping tokens, obtain stream serialization including absent first head, consume its delivery nonce, save immutable exact body and verification packet evidence, advance matching monotonic head and save actual receipt14. All-or-nothing means failed signature/local revoke/current tuple/expiry/CAS writes no nonce/snapshot/head/receipt. Use empty-search-path private definer plus service-only invoker, SELECT-only ledger grants and exact immutable/head guards. No direct service INSERT into snapshots/receipts/heads.

First admission requires a current-source proof and a newer source revision. Equal revision + identical bytes is exact replay with no second cost or head change; equal revision + changed bytes rejects. Unknown older source revision cannot fabricate a current snapshot/receipt and should fail before mutation in this first slice. Exact already committed historical replay, if supported later, is a separately reviewed local authorization path that never reactivates a head; it must not request a fictitious positive historical source proof. A stale receipt requires an actual saved newer snapshot pointer; absence never authorizes inventing one.

Receipt14 binds actual durable receipt UUID, snapshot UUID/raw SHA, requested/applied/current revisions and both full scope identities. Receiver response and durable Finance ACK must be independently reread and match all fields. Lost HTTP ACK after Finance commit retries fresh delivery nonce/same immutable bytes; no duplicate cost, no head rewind. Key/route rotation captures versioned immutable route/key identity before send; revoked routes block rather than rebind. Actual enqueue/claim/preflight/finish and reverse-version correction transport remain later contracts, not introduced by this source-proof design.

Cross-database freshness remains as-of. Operations source locks end before Finance commit; a correction or grant revoke after source verification can precede Finance admission. A short unexpired proof bounds observation age, not distributed atomicity. Finance local revoke before final SQL check blocks. Immediate remote revocation-at-Finance-commit is unsupported without a new distributed protocol; tests must assert the observation boundary rather than claim an impossible lock. Future correction delivery and explicit remote revocation policy are prerequisite to broader activation.
