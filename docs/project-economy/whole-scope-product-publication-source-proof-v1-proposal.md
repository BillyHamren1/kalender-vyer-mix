## Trusted publication transaction

The actual actor and organization derive from live auth user, unique profile and same-organization admin role. No service surrogate, caller amount, projection, raw capture, calculation version, coverage or admission boolean is accepted.

The proposed command has the nine existing TEST semantic selectors, with a NEW product schema: schema_version, economic_scope_id, expected_scope_revision, expected_membership_fingerprint, expected_composition_revision, expected_composition_fingerprint, expected_publication_revision, idempotency_key and reason. Source versions are positive safe integers; expected publication may be zero only for first publication. This is a proposal, not reuse of the TEST RPC.

1. Validate exact command and actual live admin rows, then enabled independent product publication gate under SHARE/NOWAIT.
2. Discover the immutable expected composition and membership only as hints. Collect the union of all full canonical source-project members and selected baseline projects. Lock every actual live same-tenant project in deterministic UUID order **before** the organization barriers. All hinted auth user/profile/admin, publication/read gates, live projects, actual root and current packing-policy rows use SHARE NOWAIT (or a stronger nonwaiting lock). ## Proof and recipient disclosure boundary

Proof must come from an actual saved product publication. A read service enrollment alone is insufficient to grant disclosure. A separately authenticated Operations full-scope export grant must capture actual live canonical full membership, source scope, explicit Finance organization/destination whole scope, Finance immutable mapping ID/revision and the scope actor/reason. First grant permanently reserves the source org+economic scope to exactly one Finance org+destination whole scope; disabling/revising grant or changing the current mapping event never transfers that owner or creates another economic stream. Retirement/successor ownership remains unsupported. The grant is metadata for destination selection; Finance independently rechecks its own real entity/map/share/recipient rights under locks and does not inherit permissions from it. Source aliases and guessed same-looking destination IDs remain unsupported.

Publication/export/read gates default false and are independent from legacy read gates. Config identities are immutable and service-maintained updates are enabled-only. Source snapshots/head/receipts are private, owner-written and application/service SELECT-only; owner-level immutable/no-rewind/no-delete/no-truncate guards protect saved history.

The NEW protected verification request must bind the exact canonical destination raw bytes, not merely its hash or a caller projection. The server parses strict exact23 body, resolves source publication ID/version, and compares every source token, copied projection scalar/null, redacted manifest and selected export-grant destination/mapping token to the immutable saved rows. A new mapping/body requires an actual new Operations publication revision, including when amounts are unchanged. The server does not attest Finance recipient permission or remote currentness.

The latest saved publication head is not sufficient for current-source acceptance. The proof transaction must re-capture actual current compatible evidence under the same complete nonwaiting source/permission closure, then compare every field with the saved capture except the explicitly volatile top-level `as_of` and each exact member's `kernel_evidence.as_of`. Those timestamps alone are omitted from this currentness comparison; saved capture/observation/fingerprints are never rewritten. No other field, array order, null, status, baseline, policy, source token or diagnostic is normalized away. Actual source/policy/baseline/graph changes block current proof until a new genuine publication. The first protected proof slice returns current-source snapshots only; historical saved reads/replays require a separate reviewed protocol and must never activate a Finance head.

Proposed source fingerprint bytes are UTF8 of the existing safe `operations_economy_private.canonical_json_v1` applied to purpose arrays, without BOM or trailing LF: evidence `["operations-whole-scope-product-evidence-v1", exact_saved_capture28]`; publication `["operations-whole-scope-product-publication-v1", exact_saved_product_document]`. SHA256 lowercase hex is stored. The exact product document and calculator version are still subject to root/schema lock; it binds immutable identity/revision, full membership, original observation, exact capture/projection/manifest, captured destination grant references and actual actor/command. The Finance verifier treats these private semantic fingerprints as opaque; it never reconstructs them from redacted rows. Product/SQL-to-TS Unicode/quote/newline vectors are required before implementation ACK.

The concrete candidate calculator version is `operations-whole-scope-invoice-capture-sql.v1`. The exact internal product document22 candidate keys are schema_version, publication_id, organization_id, economic_scope_id, publication_revision, actor_id, command, calculation_version, full_membership, scope_snapshot_id, scope_revision, membership_fingerprint, composition_snapshot_id, composition_revision, composition_fingerprint, capture, projection, source_manifest, source_evidence_fingerprint, observed_at, export_grant and shadow_only. Schema is `operations-whole-scope-product-publication.v1`; shadow_only=true. Full saved exact28 capture retains private evidence and original times. Export_grant is the exact7 server-captured event, or null when destination is unavailable; null blocks proof/delivery. Destination23 canonical bytes are constructed only after the document fingerprint, avoiding a circular hash, and saved in a separate immutable column tied to the same publication and captured grant. A current grant appearing/changing later requires a new genuine publication, never a rewrite of an old source record.

The signed response must carry the saved publication identity/revision and semantic fingerprints, calculation version and observation, actual full canonical membership proof, exact selected body SHA, actual export grant identity/version/fingerprint, saved current source head at verification, verification time and short expiry. The exact request2/response18/grant7 and HMAC7/8 candidate is documented in Finance `docs/project-economy/whole-scope-product-source-verification-v1-proposal.md`; it is not locked yet. No response field named verified/eligible/complete can substitute for these facts.

Use separate purpose/key namespaces from original Catering receipt lookup and cost delivery. Method/path/key/timestamp/nonce/exact raw request, and signed response binding to exact request SHA and original nonce, need dedicated HMAC lines. Request/response bodies have whole-operation monotonic deadlines, strict UTF8, byte/chunk bounds, cancellation-before-success protections and redirect refusal, reusing reviewed patterns rather than weakening them. Nonce scope is persistent across processes and rejected authorization/body/currentness rolls back consumption.

An unknown requested body that is already superseded cannot become the current Finance copy. A future historical source read requires a separate explicitly historical-only protocol; the first proof slice does not issue positive historical proofs. Finance exact committed replay must not rewind a head. Source verification is an as-of observation across two databases, not distributed atomic freshness. A later genuine Operations correction must be delivered, and unknown superseded local evidence is blocked rather than furnished with an invented snapshot pointer.

Withdrawal/retirement, successor destination, immutable routes/outbox claim/finish and copied Finance read are later explicit subcontracts. No zero snapshot, automatic historical grant revival, fake receipt or silent deletion is allowed. Until those exist, this publisher/read slice has no cost transport activation. Whole and component amounts are never added together by Finance.

## Required proof before implementation/integration

- Source audit: exact installed owner/caller/ACL closure including dynamic dispatch, full source hashes, compatible helper prerequisite and actual legacy graph limitations.
- Calculator: product private port exact52 value/error/null/overflow parity; no public/calculator input bypass and no source semantic fingerprint reconstructed from redacted rows.
- Transaction: actual authenticated writer, gate/auth/project revocation, current scope/composition/baseline/policy/source advance, absent v1/v2 counterpart and both causal lock orders. Observe genuine PostgreSQL Lock waits; timeouts/deadlocks do not count as valid conflict.
- Immutability: owner and service direct write denials, permanent source ownership, CAS conflict, exact historical replay, changed request bytes, same version/economics correction, partial/null amounts and all excluded diagnostic anchors retained.
- Protected proof: actual saved product publication through real HTTPS/PostgREST, persistent concurrent nonce, default-off/live grant revoke, scope/key/purpose/tenant/privacy boundaries and bounded cancellation/cleanup.
- Finance: genuine signed proof plus exact locally current full entity/map/share/all-member recipient rights; atomic saved verification/body/head/receipt and actual14 receipt reread. The current unconditional product-source denial is retained until this separate integration is approved and executed.

Native52 prototype parity, native TEST transaction/TRY results and native original13 lookup are useful prerequisites. None individually establishes this product source authority or complete economic coverage.
