# Exact-Node24 static server and long-lived owned-process boundary

Status: **additive source candidate; pure/local support tests only; exact native launch, browser and release remain HOLD**.

This successor removes ambient Python from the full-App static transport. The server is an ES module executed only when the purpose variable `COMPATIBLE_FULL_APP_NODE_STATIC_SERVER=1` is present. Its owner constructs the command exclusively from the already-open exact Node executable FD and server-source FD: `/proc/self/fd/<node>` executes `/proc/self/fd/<source>`, with the held dist-directory and fresh held receipt FDs as the only arguments. `PATH` cannot select Node. The Node evidence is canonical, outer-hashed bytes binding reviewed policy `978007cda2664e5fccd1974b377b0cf35f35c33a0a2e3253f5685d2f92c1d8bd`, Node24 successor `100c5a67bf3c2ade6f3b53cb105d8f38bc47cb012f329bc60258c6e94592cfee`, archive `fd8e59d5a511510f6a298afb548f18c7d2b1be404d8b4a27d94fbe49f56cb2d6`, version `v24.21.0`, archive root and `bin/node`. The executable content SHA-256 and byte count must come from authenticated extraction evidence and are rehashed through the held FD before launch and again after cleanup. They are deliberately not invented here.

The Node server retains the reviewed Python server's transport semantics: IPv4 `127.0.0.1`, OS-assigned port, fixed economy project route, canonical owner-only receipt schema, GET/HEAD only, exact Host, no request body, transfer encoding, Expect or Range, finite header/target/request/deadline limits, no directory listing, no API/auth/provider proxy and no provider or login operation. It inventories the held dist FD with bounded per-directory name lists and total entry/depth/byte/file limits. Every child is opened relative to a still-held parent FD through `/proc/self/fd`, with `O_NOFOLLOW` and pre/open/post identity checks. Selected assets are read from held FDs after all ancestors and root are rebound. HTML is no-store, fixed hashed assets immutable, and only `/`, `/index.html` and the fixed project route fall back to index. The server verifies native PID/PGID/SID equality from `/proc/self/stat`; virtualized PID views cannot produce a native positive.

The separate Python owner derives from frozen b901 custody SHA-256 `b9011bfd85b7af59057892bef9b628514367e84cd12a2c5b8d168a2b77721c7a` but does not call its six-second `run_owned` helper. It uses the same pre-exec acquisition record, new session, actual `Popen` handle, PID/start-time leader validation, retained `UNCERTAIN_CHILDREN` entry and b901 `stop_owned` cleanup kernel. A successful start returns a privately registered strong handle only after canonical server receipt bytes match the acquired PID/PGID/SID and held dist device/inode. `check_static` revalidates the leader, exact retained FDs, unchanged receipt bytes and unreaped liveness. The handle and uncertainty record survive launch and browser work; they are removed only after b901 proves group absence and its one-way reap receipt is complete.

Cleanup reads stdout/stderr through the original held stream FDs, never replaceable pathnames, and verifies their shapes and pre/post identities. It accepts exactly one bounded server CLOSED line and empty stderr. After cleanup it rehashes the exact Node and server source FDs and rechecks the held dist identity before writing an exclusive closed record. Any ambiguous start or cleanup retains failure and ownership state; a numeric PID alone never authorizes signaling.

Local Node tests cover FD-bound inventory/read behavior, symlink and mutation refusal, fixed routing/cache policy, request grammar, Range denial and canonical receipt bytes. Local Python tests cover canonical Node evidence, content-bound FD checks, canonical owner/dist receipt matching, fixed HOLD CLI, and a protocol-double lifecycle showing the strong handle plus PID/start-time survive start and check until b901-style cleanup. These tests used ambient Node only as a support-test interpreter and do not claim the required `v24.21.0` executable, real kernel custody or a live loopback server. The current container exposes a virtualized PID view, which the real server correctly refuses.
