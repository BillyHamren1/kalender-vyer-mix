This is concrete missing participation, not just a hypothetical absent row. Other current named-function writes and application/direct DML remain separate full writer-inventory work; these two examples alone invalidate a blanket common-advisory assumption.

The official [PostgREST12.2 transaction documentation](https://postgrest.org/en/v12/references/transactions.html) supports per-function `default_transaction_isolation` for an RPC request. PostgreSQL15 [Repeatable Read](https://www.postgresql.org/docs/15/transaction-iso.html) gives the transaction one stable snapshot and can raise serialization failures when locking a row changed after its snapshot. This is a candidate mechanism for membership predicate snapshot consistency combined with TRY/NOWAIT admission; it is not current implementation authority or latest upstream source completeness.

Direct SQL is a distinct compatibility issue: a function SET of default_transaction_isolation does not upgrade the already running READ COMMITTED transaction that invoked it. A private embedded supplement confirmed that such a function still observes `read committed` in a default SQL SELECT and `repeatable read` only when its caller explicitly began that level. Existing owner writer chains must remain on their original transaction semantics; they cannot be silently switched or rejected by a generic new helper. Root/reviewer must decide exact standalone direct-call compatibility, RPC metadata/native cache behavior, same-TX owner recursion, and serialization/error behavior before selecting this mechanism.
